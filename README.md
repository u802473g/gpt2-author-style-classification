# GPT-2 による著者スタイル分類

小説本文から切り出した短い断片だけを手がかりに、**それが誰の書いた文章か**を GPT-2 で判別する個人研究です。
大学のゼミで取り組みました。

事前学習済み GPT-2 に対して「**どこまでの層を更新するか**」を 1 ブロックから 6 ブロックまで動かし、
さらに最適化手法を組み合わせて検証しています。最終成績は **Test Accuracy 86.86%**（5クラス）。

このリポジトリは最終的な数字だけでなく、**うまくいかなかった条件とその原因**も残しています。

---

## 何をしたか

| | |
| :--- | :--- |
| **入力** | 小説本文からスライディングウィンドウで切り出した断片（200 語、可変長の系列もあり） |
| **出力** | その断片を書いた著者 — Dickens / Doyle / Twain / Wells / Others の 5 クラス |
| **データ** | Hugging Face 経由の Gutenberg Fiction Corpus。各クラス 2,500 件、計 12,500 件 |
| **モデル** | 事前学習済み GPT-2 small (124M) を中心に、medium (355M) / large (774M) も比較 |
| **比較軸** | 更新するブロック数（1〜6）× 最適化手法（学習率・ウォームアップ・コサイン・勾配クリップ・dropout）、および LoRA の有無 |
| **制約** | Google Colab の無料枠に収まること。これがモデルサイズとデータ量の上限を決めている |

この課題の難しさは、判別の手がかりが「何が書かれているか」ではなく**文体**である点です。
同じ著者でも作品ごとに話題は変わるため、語彙の選び方・句読点の打ち方・一文の長さといった
表層の癖を捉える必要があります。

## なぜやったか

出発点は、教科書で GPT-2 を実装していたときに引っかかった一点です。

分類タスクのファインチューニングでは、慣例的に「出力層と、最後の LayerNorm と、
最後の Transformer ブロックだけを訓練可能にする」という設計が採られます。
計算効率の観点からは妥当ですが、**それが精度の面でも最適だとは説明されていませんでした**。

> 更新する層を増やしたら、精度はどう変わるのか。増やすほど良くなるのか、どこかで悪化するのか。

これを確かめるには、層の使い方の差が精度に表れるタスクが要ります。
そこで選んだのが著者スタイル分類でした。文体は意味内容より浅い層に現れる特徴だと考えられるため、
**「どの深さの層を動かすか」が結果に直結する**はずだ、という見立てです。

見立ては当たりました。同じモデル・同じデータでも、更新するブロック数だけで精度が **9.4 ポイント**動き、
しかも単調には動かず、途中で反転しました。

## 結果

### 更新ブロック数を動かす（中心的な結果）

GPT-2 124M・5クラス・12,500 件。他の条件は固定し、更新範囲だけを変えています。

| 更新範囲 | Test Acc |
| :--- | :---: |
| 最終1ブロック（慣例的な設計） | 76.29% |
| 最終2ブロック | 81.32% |
| 最終3ブロック | 82.38% |
| 最終4ブロック | 84.78% |
| **最終5ブロック** | **85.67%** |
| 最終6ブロック | 83.05% |

**5 ブロックまでは単調に上がり、6 ブロックで下がります。**
慣例の「最終1ブロックのみ」はこのタスクでは明確に不足しており、その差は 9.4 ポイント。
一方で全層に近づければ良いわけでもなく、最適値は途中に存在します。

深い層ほどタスク固有の表現を、浅い層ほど汎用的な言語構造を持つとすれば、
文体を捉えるには 5 ブロック分の深さが要るが、それ以上遡ると
壊してはいけない汎用表現まで更新してしまう、という読み方になります。

### 最適化手法を足す

上で最良だった 5 ブロック解凍を土台に、手法を1つずつ足した結果です。

| 追加した要素 | Test Acc |
| :--- | :---: |
| （5ブロックのみ） | 85.67% |
| 学習率 2e-5 へ引き下げ | 85.59% |
| ウォームアップのみ | 86.14% |
| コサインのみ | 85.59% |
| ウォームアップ + コサイン | 84.36% |
| 勾配クリップ | 85.97% |
| **dropout 0.1** | **86.86%** |
| ウォームアップ + dropout 0.1 | 84.11% |
| ウォームアップ + 勾配クリップ0.5 + dropout 0.1 | 84.70% |

ここで2つのことが分かりました。

**1. 正則化が効くかどうかは更新範囲に依存する。**
同じ dropout 0.1 が、最終1ブロックの構成では 70.50%（ベース 76.29% から **−5.8pt**）、
最終5ブロックの構成では 86.86%（ベース 85.67% から **+1.2pt**）と、逆に働きました。
表現力が足りていない段階で正則化を足すと、足りないものがさらに減るだけです。

**2. 効いた手法を足し合わせても加算にならない。**
dropout 単体の 86.86% に対し、ウォームアップを足すと 84.11% に落ちます。
個別に効いた要素が互いの効果を打ち消しました。

詳細な条件と全試行は [アブレーション結果](docs/ablation-results.md) にあります。

### モデルサイズと LoRA

別系列として、モデルサイズと LoRA の有無も比較しています（全 17 条件は [実験サマリ](docs/experiment-summary.md)）。

| 実験 | モデル | 方式 | Test Acc |
| :--- | :---: | :---: | :---: |
| `bungo_124M_no_lora_4class` | 124M | 部分微調整 | 81.85% |
| `bungo-124M-lora-4class` | 124M | LoRA | 80.05% |
| `bungo-355M-lora` | 355M | LoRA | 77.60% |
| `bungo-355M-variable` | 355M | 部分微調整 | 61.92% |
| `bungo-774M-variable` | 774M | 部分微調整 | 58.10% |

- **355M では LoRA がないと崩れる。** 同じ更新範囲で 61.92% → 77.60% と 15 ポイント以上の差。
  ここでの LoRA は計算量削減ではなく、**低ランク正則化**として働いています
- **774M では 58.10% まで落ちる。** データ量が Colab の制約で頭打ちな以上、
  モデル容量だけ増やしても適合先がありません

## 開発の過程

データ設計の側でも遠回りをしています。初期の 57.50% から、
クラス不均衡の解消とデータ量の確保で 80.18% まで引き上げました。

| 段階 | 変更点 | Test Acc |
| :--- | :--- | :---: |
| 第1段階 | 初期設計（200語・4,000件・クラス不均衡） | 57.50% |
| 第2段階 | 入力を100語に短縮 → **悪化** | 53.00% |
| 第3段階 | 200語に戻し、クラス均等化・更新を最終2ブロックに拡大 | 76.55% |
| 第4段階 | 12,500件までスケールアップ | 80.18% |

第1段階では、パディング位置の出力を分類に使ってしまい、
短い入力がすべて `Others` に倒れる**パディング汚染バグ**を踏んでいます。
第2段階の「過学習を抑えようとして入力を短くしたら、かえって悪化した」も含め、
経緯は [開発ログ](docs/development-log.md) に分けて書きました。

## 再現するには

Google Colab の無料枠（T4）で完走する構成です。実装の要点は以下のとおりで、
[アブレーション結果](docs/ablation-results.md) の各行がそのままハイパーパラメータになっています。

**データ**

- Hugging Face 経由で Gutenberg Fiction Corpus を取得
- 著者ごとに本文を集め、200 語のスライディングウィンドウ（ステップ 50）でスニペット化
- Dickens / Doyle / Twain / Wells / Others の 5 クラスを各 2,500 件に均衡させる（計 12,500 件）
- Train / Val / Test = 8,750 / 1,250 / 2,500

**モデル**

- OpenAI 公開の GPT-2 124M チェックポイントを読み込む
- `trf_blocks[-5:]` のみ `requires_grad=True`、残りは凍結
- 出力ヘッドを `Linear(768, 5)` に差し替え
- dropout 0.1、学習率 5e-5、AdamW、3〜5 エポック、バッチサイズ 8

**分類時の注意点**

系列の最後のトークン位置の出力を分類に使いますが、バッチ内でパディングすると
**パディング位置を読んでしまい、短い入力が多数派クラスに倒れます**。
系列ごとに最後の実トークン位置を動的に取り出す処理が要ります
（この事故の詳細は [開発ログ](docs/development-log.md)）。
