# 開発ログ — データ設計側の試行錯誤（57.50% → 80.18%）

最終的な精度そのものより、**何がうまくいかず、なぜそうなり、どう直したか**を残すための記録。
各段階で判断の根拠にした数値と、そこで踏んだ失敗を時系列で並べている。

このログが扱うのは**データ設計側**（スニペット長・クラス均衡・サンプル数）の試行錯誤。
更新ブロック数と最適化手法の検証は [アブレーション結果](ablation-results.md) に分けてある
（そちらが最終成績 86.86% に至る系列）。

---

## 1. 4段階の変遷（5クラス・GPT-2 124M）

| 段階 | スニペット長 | 1クラスあたり | 総サンプル | Train / Val / Test | Test Acc | この段階で起きたこと |
| :--- | :---: | :--- | :---: | :---: | :---: | :--- |
| 第1段階<br>初期設計 | 200 語 | ターゲット4名 各500<br>Others 2,000 | 4,000 | 2,800 / 400 / 800 | **57.50%** | 過学習。加えて、短い入力がすべて `Others` に倒れる**パディング汚染バグ**が発生 |
| 第2段階<br>長さ調整の試行 | 100 語 | ターゲット4名 各500<br>Others 2,000 | 4,000 | 2,800 / 400 / 800 | **53.00%** | スニペットを短くしたら悪化。文体特徴が落ち、入力と正解の相互情報量 $I(X;Y)$ が下がった |
| 第3段階<br>情報量の復元と増強 | 200 語 | 全クラス均等 各1,500 | 7,500 | 5,250 / 750 / 1,500 | **76.55%** | 長さを戻し、クラス不均衡を解消。更新対象を最終2ブロックに広げて表現力を確保 |
| 第4段階<br>スケールアップ | 200 語 | 全クラス均等 各2,500 | 12,500 | 8,750 / 1,250 / 2,500 | **80.18%** | Colab のリソース制限内で可能な限りデータを増やし、80% を突破 |

### 第1段階の失敗：パディング汚染

入力長がばらつく状態でバッチを組んだ結果、短いスニペットではパディングトークンの位置の出力を
分類に使ってしまい、**内容に関係なく多数派クラス（`Others`）へ倒れる**状態になっていた。
系列ごとに「最後の実トークン位置」を動的に取り出す処理（`get_last_active_logits`）を入れて解消している。

### 第2段階の失敗：短くすれば汎化するという誤り

過学習への対処としてスニペットを 200 語から 100 語へ短縮したところ、精度は 57.50% → 53.00% と**下がった**。
文体の判別に効く特徴（語彙の選択、句読点の打ち方、一文の長さ）は一定の長さがないと現れない。
過学習の原因は入力の長さではなくデータ量とクラス不均衡の側にあった、というのがこの段階の結論。

## 2. 学習容量とデータ量の釣り合い

同じ 124M でも、**更新するブロック数**と**データ量**の組み合わせで結果が変わる。

| 更新対象 | データ量 | スニペット長 | 結果 |
| :--- | :---: | :---: | :--- |
| Block 11 のみ | 4,000 | 200 語 | 過学習 |
| Block 11 のみ | 4,000 | 100 語 | 情報量不足でアンダーフィット（53.00%） |
| Block 10–11 | 7,500 | 200 語 | 釣り合いが取れる（76.55%） |
| Block 10–11 | 12,500 | 200 語 | この構成での最良（80.18%） |

モデル側の自由度だけ、データ側の情報量だけを動かしても頭打ちになる。
「なぜ $L=200$ なのか」「なぜ $N=12{,}500$ なのか」は、この対応表から逆算して決めている。

## 3. 最終構成のパイプライン

```
[Hugging Face Gutenberg Fiction Corpus]
              │
              ▼  可変長スライディングウィンドウ
              │  Length = random(30, 200), Step = 50
[均衡データセット: 5クラス × 2,500 = 12,500 サンプル]
              │
              ▼  BPE トークナイザ + バッチ単位の動的パディング
[GutenbergDataset  (batch size = 8)]
              │
              ▼
┌────────────────────────────────────────────┐
│ GPT-2-small (124M)                         │
│   Blocks 0-9   : 凍結 (requires_grad=False)│
│   Blocks 10-11 : 更新 (requires_grad=True) │
└──────────────────┰─────────────────────────┘
                   │  出力ロジット [B, T_max, 768]
                   ▼
   [get_last_active_logits — 系列ごとに最終実トークンを動的抽出]  → (B, 768)
                   │
                   ▼
   [分類ヘッド Linear(768, 5)]                                    → (B, 5)
                   │
                   ▼
   [Cross Entropy Loss / Accuracy]
```

固定長ではなく `random(30, 200)` の可変長にしたのは、推論時に入力長が揃っている保証がないため。
学習時から長さのばらつきに曝しておくことで、短い入力でも崩れないようにしている。

## 4. 条件を振った結果

可変長スニペット（30–200 語）に移行してからの比較。

**更新ブロック数の影響（LoRA あり）**

| モデル | 更新ブロック | データ量 | Train | Val | Test |
| :--- | :--- | :---: | :---: | :---: | :---: |
| 124M | Block 11 のみ | 12,500 | 66.25% | 56.25% | 66.95% |
| 124M | Block 10–11 | 12,500 | 98.75% | 66.25% | 72.20% |
| 124M | Block 10–11 | 7,500 | 86.25% | 62.50% | 63.80% |
| 355M | Block 23 のみ | 12,500 | 100.00% | 81.25% | **77.60%** |
| 355M | Block 22–23 | 12,500 | 90.00% | 65.00% | 70.44% |

355M では 1 ブロックの方が 2 ブロックより良い。容量を増やすほど良くなるわけではない。

**355M で LoRA を外すと崩れる**

| モデル | 手法 | Test |
| :--- | :--- | :---: |
| 355M | LoRA なし（Block 23） | 61.92% |
| 355M | LoRA あり（Block 23） | **77.60%** |

同じ更新対象でも 15 ポイント以上の差がつく。LoRA がパラメータ削減の手段としてではなく、
**低ランク正則化**として効いていることを示す結果。

**dropout と LoRA ランク（4クラス・124M・LoRA）**

| データ量 | dropout | rank | Test |
| :---: | :---: | :---: | :---: |
| 20,000 | 0.0 | 16 | 79.42% |
| 20,000 | 0.2 | 16 | 61.50% |
| 4,000 | 0.1 | 16 | 71.88% |
| 4,000 | 0.1 | 8 | 66.50% |

dropout 0.2 は明確に過剰。ランクを 16 → 8 に落とすと 5 ポイント下がり、
この課題では低ランク側の表現力がすでに効いていることがわかる。

**4クラスでの最良**

| 手法 | エポック | Train | Val | Test |
| :--- | :---: | :---: | :---: | :---: |
| LoRA なし | 3 | 81.25% | 81.25% | 77.45% |
| LoRA なし | 5 | 98.75% | 83.75% | 81.00% |
| LoRA あり | 5 | 100.00% | 77.50% | 80.05% |
| LoRA なし（10,000件） | 5 | 100.00% | 87.50% | **81.85%** |

**うまくいかなかった試み**

- Mean Pooling への変更 … 71.68%。最終実トークンを使う方式を上回らなかった
- コサインアニーリングを 4,000 件の構成に適用 … 43.62% まで低下。データ量が足りない状態では
  学習率スケジュールを凝っても意味がなく、むしろ収束を壊した

## 5. この先

データ量とクラス均衡を整えたことで 80% 台に乗ったが、ここから先は
**更新するブロック数を広げる**方向で伸びた。その検証は
[アブレーション結果](ablation-results.md) にまとめてある（最終 86.86%）。

未実行のまま残しているのが `bungo-senryaku1`。
最終ブロック単体の出力ではなく、より素の文体・構文特徴が残る中間層（Block 9, 10）の
隠れ状態を加重平均して分類ヘッドに入れる構成で、3ブロック解凍分を Weight Decay 0.25 で抑える設計。
